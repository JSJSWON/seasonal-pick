# seasonal-pick 설계 문서

최초 작성 2026-10-25 · 개발 진행에 따라 계속 갱신

## 1. 서비스

### 1.1 해결하려는 문제

장을 볼 때 재료의 **절대 가격만** 보고 판단하게 된다. 과거에 얼마였는지 모르니
"오이 5개 1000원"이 싼 건지 알 수 없고, 할인율 20%가 실제로 싼 건지도 모른다.
제철 여부도 찾아보지 않으면 모른다.

이 서비스는 두 가지에 답한다.

1. **이 가격이 평소보다 싼가, 비싼가** — 계산해서 제공
2. **지금이 맛있는 시기인가** — 별도 정보로 제공

### 1.2 두 축은 독립이다

**제철(맛)과 가격(돈)은 서로 다른 축이며, 가격에서 제철을 유도할 수 없다.**
저장 물량이 풀려 싼 시기가 맛있는 시기는 아니고, 제철 초입에는 맛이 절정인데
물량이 적어 비쌀 수 있다.

|            | 싸다 ○            | 싸다 ✕                  |
| ---------- | ----------------- | ----------------------- |
| **제철 ○** | 지금 사라 (목표)  | 맛은 좋을 때, 값은 비쌈 |
| **제철 ✕** | 저장품·수입. 주의 | 살 이유 없음            |

가격만 보여주는 서비스는 사용자를 왼쪽 아래 칸으로 밀어넣는다. 두 축을 함께
보여주는 것이 이 서비스의 존재 이유다.

### 1.3 MVP 범위

**가격 추세 하나**를 제대로 만든다. 제철·보관법·조리법은 그 다음이다.

- 부류별 1개씩, 실제로 데이터가 있는 5부류
- 지역 선택 (전 지역 수집)
- 월별 추세선 + 현재 가격 위치 + 평년 대비 판정

### 1.4 MVP 대상 품목

부류를 고루 건드려 스키마의 일반성을 검증하는 것이 선정 기준이다.

| 부류          | 품목       | 코드      | 품종                                  | 등급        |
| ------------- | ---------- | --------- | ------------------------------------- | ----------- |
| 100 식량작물  | 쌀         | `111`     | `01` 20kg                             | `04` 상품   |
| 200 채소류    | 배추       | `211`     | `01` 봄 `02` 여름 `03` 가을 `06` 월동 | `04` 상품   |
| 300 특용작물  | 새송이버섯 | `317`     | `00` 새송이버섯                       | `04` 상품   |
| 400 과일류    | 복숭아     | `413`     | `01` 백도                             | `04` 상품   |
| 600 수산물    | 김         | `641`     | `00` 마른김                           | `30` (이름 없음) |

**축산물(500)은 빠졌다.** 부류 전체의 소매가격이 2022년까지만 제공되고 2023년부터
0건이다(3.2-타). 품목을 바꿔도 해결되지 않으므로 MVP는 5부류로 간다.

**등급이 품목마다 다르다.** `04 상품`이 김에는 없다. 전역 상수로 등급을 고정하면
그 품목들의 수집 결과가 0건이 된다. 김은 한 걸음 더 나가서, 코드표에 없는 등급
`30`으로 제공된다(3.2-파).

쌀 품종 `01`(20kg)과 `05`(20kg 햅쌀)는 별개이며 햅쌀은 가을 한정이다. 연중
추세를 보려면 `01`을 쓴다.

## 2. 시스템 구성

```
[Next.js]  화면 · 그래프                      web/
    │ HTTP (JSON)
    ▼
[ASP.NET Core Web API]  조회 + 판정 로직       api/
    │
    ▼
[PostgreSQL]  가격 이력 · 마스터
    ▲
    │
[수집 워커]  공공데이터 API → DB               collector/
```

**원칙: 수집과 조회를 분리한다.** 사용자 요청이 외부 API를 직접 호출하지 않는다.
외부 API는 일일 호출 한도가 있고 잔여량을 조회할 수단이 없다.

DB의 역할은 "없는 데이터를 만드는 것"이 아니라 **다시 받는 비용을 없애는 것**이다.
두 API 모두 기간 조회를 지원하므로 과거를 되받을 수는 있지만(9절), 화면을 그릴
때마다 수천 건을 다시 받을 수는 없다.

수집기는 **콘솔 앱**이다(`collector/SeasonalPick.Collector`). 백필은 한 번 돌고
끝나는 작업이라 호스팅 수명주기가 필요 없고, 2단계에서 스케줄이 필요해지면 지금
만든 클래스들을 호출하는 워커를 덧붙인다. `api/`와는 솔루션을 나눈다 — 함께 빌드할
일이 없고, 수집기는 화면 없이 단독으로 돈다.

## 3. 데이터 소스

### 3.1 사용 API — 2개

| API                                | 역할                           | 우리가 받을 범위           | 주기                        |
| ---------------------------------- | ------------------------------ | -------------------------- | --------------------------- |
| **연월별 도·소매가격정보 조회**    | 평년값 · 산포 · 월별 추세      | 전 지역 · 5년 · `se_cd=01` | 월 1회                      |
| **지역별 품목별 도·소매가격정보 조회** | 일별 현재가 · 최저~최고       | 전 지역 · 1년 · `se_cd=01` | 매일 + 최근 2~3주 재동기화 |

**"범위"는 우리 수집 정책이지 API의 한계가 아니다.** 지역별 품목별도 5년 전을
닿는다(서울 쌀 2021년 248건). 일별을 1년만 받는 것은 화면이 1년 추세만 쓰고,
5년치 일별은 27만 행이 되기 때문이다.

```
GET https://apis.data.go.kr/B552845/perYearMonth/price    연월별
GET https://apis.data.go.kr/B552845/perRegion/price       지역별 품목별
```

판정의 근거는 **연월별** 하나에서 나온다. 지역별 품목별은 현재 상태 표시용이다.

둘 다 `cond[필드::GTE/LTE]` 형태의 기간 조회를 지원하고, 2020년 데이터가 있으며,
응답에 `totalCount`를 제공한다. 백필과 페이징 루프가 성립한다. `numOfRows`의
상한은 **1000**이다(지역별은 명세에 명시, 연월별은 실제 호출로 확인).

**필수 파라미터가 두 API에서 다르다.**

```
공통      serviceKey · returnType · pageNo · numOfRows
연월별    + 없음
지역별    + cond[exmn_ymd::GTE] · cond[sgg_cd::EQ]
```

`numOfRows`는 기본 10, 최대 1000. `pageNo` 기본 1. `returnType` 기본 JSON이며
XML을 받으려면 대문자 `XML`로 준다. `selectable`에 컬럼명을 쉼표로 나열하면 응답
컬럼을 골라 받을 수 있다.

**명세 엑셀이 실제와 어긋나는 곳이 두 군데 있다.** `numOfRows`의 최댓값이 지역별
명세에만 적혀 있고 연월별 명세에는 빠져 있다. 그리고 `cond[sgg_cd::EQ]`가 선택으로
적혀 있지만 지역별에서는 사실상 필수다 — 포털 화면에는 필수 표시가 있다.

**두 API의 코드 체계는 동일하다** (코드표 6개 파일이 바이트 단위로 같음).

### 3.2 확인된 API 특성

실제 응답을 보고 확인한 사실만 적는다. 설계가 이 사실들에 의존한다.

**(가) 환산가격 공식**

```
cnvs_*_prc = *_prc / unit_sz    (단위는 unit, 반올림)

 47,500 / 20 = 2,375      201,143 / 40 = 5,029
118,000 / 40 = 2,950      155,000 / 35 = 4,429
```

`unit`은 품목마다 다르다(쌀 kg, 배추 포기). **aT가 kg 환산을 해주므로 품목 간
비교가 가능하다.** 포기→kg은 우리가 무게를 모르면 불가능하다.

**(나) 과거 날짜 데이터가 나중에 등록된다**

| 조사일 | 등록 시점   | 지연  |
| ------ | ----------- | ----- |
| 10/01  | 10/01 15:16 | 당일  |
| 10/06  | 10/13 16:11 | 7일   |
| 10/08  | 10/13 16:31 | 5일   |
| 10/22  | 10/22 15:06 | 당일  |

**"빈 날짜만 채우기"로는 부족하다.** 10/7에 수집했다면 10/6을 "조사 없음"으로
잘못 확정했을 것이다. 최근 구간을 매번 다시 받아 덮어써야 한다.

당일 데이터는 15시 전후에 등록되므로 수집은 밤에 돌린다.

**단, 이 표의 근거는 9절에서 쓰지 않기로 한 시장 단위 API(`periodRetail`)의
응답이다.** 우리가 쓰는 `perRegion`의 응답에는 `orgnl_reg_dt`가 없어 같은 방식으로
재확인할 수 없다(명세와 실제 응답 모두 확인). 등록 지연 자체는 aT의 수집
파이프라인 성질이라 집계 API에도 적용될 것으로 보이지만, 확인 수단은 "어제
비었던 날짜가 오늘 채워졌는가"를 직접 관찰하는 것뿐이다(7-⑨).

**(다) 조사는 평일만 이뤄진다**

2026년 10월 서울·쌀 조사일을 전수 확인한 결과 토·일이 0건이고, 평일 중
**10/5(개천절 대체공휴일)과 10/9(한글날)만** 빠졌다.

**(라) 품종이 계절에만 존재한다**

조회 범위를 9월부터 줘도 "20kg(햅쌀)"은 10월부터 데이터가 나오고, 가을배추는
11월부터 나온다. 품종이 아예 없는 기간이 몇 달씩 이어진다.

**(마) 등급코드는 전역에서 유효하지 않다**

```
등급코드 "1"  →  1++등급 · 삼겹살 · 갈비 · 미국산 · 일반란 · 육계(kg) · …  (12가지)
"M과"         →  14, 15, 25 세 코드
"01" = 1등급  ≠  "1" = 1++등급
```

`grd_cd` 단독으로는 의미가 없고 **(품목, 품종, 등급) 복합으로만** 해석된다.
그리고 `"01"`과 `"1"`이 다른 등급이므로 **정수로 변환하면 데이터가 섞인다.**

**(바) 품목코드 길이가 고정이 아니다** — 3자리 129개, 4자리 7개(`4301 소`, `9901 닭` 등)

**(사) 시군구코드에 두 계층이 섞여 있다**

```
광역  3100 경기 · 3201 강원 · 3300 충북 · 3400 충남 · 3500 전북 · 3600 전남 · 3700 경북 · 3800 경남
시    3111 수원 · 3112 성남 · 3113 의정부 · 3138 고양 · 3145 용인 · …
특수  9998 온라인 · 1000 전국(축산부류한정)
```

**경기(3100)와 수원(3111)을 합산하면 중복이다.** 지역 선택 UI에서 계층을 구분해야
한다. `9998 온라인`은 성격이 달라 일반 지역 목록에 섞지 않는다.

**(아) 친환경은 구분코드로도 분리된다**

`se_cd`는 `01 소매 / 02 중도매 / 03 친환경농산물 / 07 친환경농산물(신규)`이다.
표고버섯은 등급이 유기농·무농약뿐이고 **소매(`01`)에 데이터가 없다.** 그래서
MVP 품목에서 새송이버섯으로 교체했다. `se_cd`도 품목별로 지정 가능해야 한다.

**(자) 응답 형태 — 값이 전부 문자열이고 필드명이 우리 컬럼명과 다르다**

```
response.body.items.item[]        ← 껍데기가 세 겹이다
response.header.resultCode/resultMsg
response.body.totalCount/numOfRows/pageNo
```

`"pmm_avgprc":"59715"` 처럼 **숫자도 문자열로 온다.** 행이 1건일 때도 `item`은
배열로 왔다(호출 3건에서 확인).

| 연월별 응답     | 우리 컬럼     | 지역별 품목별 응답     | 우리 컬럼      |
| --------------- | ------------- | ---------------------- | -------------- |
| `pmm_avgprc`    | `m_avg_prc`   | `exmn_dd_min_prc`      | `min_prc`      |
| `pmm_hgprc`     | `m_max_prc`   | `exmn_dd_avg_prc`      | `avg_prc`      |
| `pmm_lwprc`     | `m_min_prc`   | `exmn_dd_max_prc`      | `max_prc`      |
| `pmm_stddvtn`   | `m_stddev`    | `exmn_dd_cnvs_min_prc` | `cnvs_min_prc` |
| `pmm_cfcntvrtn` | `m_cv`        | `exmn_dd_cnvs_avg_prc` | `cnvs_avg_prc` |
| `pmm_cfcntrng`  | `m_amplitude` | `exmn_dd_cnvs_max_prc` | `cnvs_max_prc` |
| `pyy_*`         | `y_*` (동일)  | —                      | —              |

변환은 수집기의 `At/` 계층이 담당한다. **API 필드명이 바뀌어도 DB 컬럼명은
그대로 둘 수 있도록** 두 이름을 분리해 둔다.

**(차) 지역 조건을 생략하면 전 지역이 온다**

연월별에서 쌀(`100/111/01/04`, `se_cd=01`) 5년(202101~202512)을 조회한 결과다.

```
sgg_cd 생략      totalCount 1,256     지역 24종
sgg_cd = 1101    totalCount    60     서울, 60개월 전부 존재
```

**지역을 38번 돌 필요가 없다.** 1회 조회로 전 지역이 오므로 호출 수가 지역 수만큼
줄어든다. 그리고 1페이지(1000행)에 49개월이 담겨, 5년을 한 번의 조건으로
요청하는 것이 성립한다.

실제로 나온 24개 지역에 **광역도 코드(`3100` 경기, `3201` 강원 등)가 하나도 없다.**
광역시 8개와 시 단위 15개, 그리고 제주(`3911`)뿐이다. 쌀 소매에 한정된 관찰이며
다른 품목은 백필 결과로 판명된다(7-③).

지역별 결손은 균일하지 않다. 서울은 60개월이 꽉 찼지만 1,256 ÷ 24 ≈ 52개월이므로
**지역마다 빠진 달이 다르다.** 판정 시 기준값 표본 수를 함께 봐야 한다.

**지역별 품목별은 정반대다.** `cond[sgg_cd::EQ]`를 생략하면 0건이 오고, 오류가
아니라 `resultCode "0" · resultMsg "정상"`과 함께 온다.

```
perRegion, 2026-10, 쌀 20kg
  날짜 + 지역 1101      6,741건
  날짜 + 부류만             0건     ← 정상 응답
```

두 API가 같을 것이라 가정하고 일별 수집기를 짜면, 매일 밤 정상 응답으로 0건을
받아 전부 `no_survey`로 확정하게 된다. 그래서 2단계는 지역마다 호출해야 하고
`대상 × 지역 24`가 하루 호출 수가 된다.

특수 지역코드 `1000`(전국, 축산부류한정)과 `9998`(온라인)에는 이 API의 데이터가
없다. 쌀로도 축산물로도 0건이다. 지역 목록에서 빼도 된다.

페이징은 정확하다. 쌀 5년을 끝까지 받아 `totalCount` 1,286과 실제 1,286행이
일치했고 중복이 없었다. 루프 종료를 `totalCount`에 걸어도 된다.

**(카) 두 API의 가격은 같은 척도다**

판정은 평년값을 연월별에서, 현재가를 지역별 품목별에서 가져와 비교한다. **서로
다른 API의 숫자를 빼는 셈이므로 척도가 같아야 한다.** 서울 2026년 8월로 확인했다.

```
쌀 20kg     일별 20건의 평균 60,488   월별 m_avg 60,488   차이 0.00%
            일별 최저~최고 60,475~60,600   월별 m_lw/m_hg 60,475/60,600
김 마른김   일별 20건의 평균  1,348   월별 m_avg  1,348   차이 0.02%
단위        양쪽 모두 kg 20 · 장 10
```

**월별 통계는 일별 값에서 그대로 유도된다.** `m_lwprc`·`m_hgprc`는 그 달 일별
평균가의 최소·최대다. 따라서 두 API를 섞어 써도 되고, 월별 백필이 일별 수집보다
먼저 와도 축이 어긋나지 않는다.

같은 표본에서 `min`/`avg`/`max`가 모든 일자에 서로 달랐다(20일 중 0일만 동일).
지역 집계인데도 범위가 남아 있으므로 "최저~최고" 표시가 가능하다(7-① 해결).

**(타) 축산물 소매는 2023년부터 제공되지 않는다**

```
축산물(500) 소매, 연도별 건수
  2021  4,048    2022  1,252    2023~2026  0
```

품목이 아니라 **부류 전체**다. `9901 닭`, 다른 등급, 모든 시군구코드(`1000` 포함),
그리고 지역별 품목별 API까지 전부 0건이다. 2026년에 남은 것은 친환경(`se_cd` 03)
27건과 친환경 신규(07) 89건뿐인데, 이는 일반 소비자가 마주하는 가격이 아니다.

2022년까지의 데이터는 그대로 받을 수 있으므로, 과거 분석이 필요해지면 되살릴 수
있다. 수집 대상 행은 지우지 않고 `is_active = false`로 둔다.

**(파) 코드표가 응답보다 불완전하다**

aT가 응답으로 내보내는 코드 중 일부가 aT 자신의 코드표 엑셀에 없다. 6부류 최근
1년 35,664행을 훑은 결과다.

```
응답에서 본 (부류,품목,품종,등급) 조합   209개
그중 코드표에 없는 조합                  37개
    등급만 없음 27 · 품종까지 없음 8 · 품목까지 없음 4
```

김 마른김이 대표적이다. 코드표는 등급 `05 중품`만 싣고 있지만 **실제 데이터는 등급
`30`으로 6년 내내 제공된다**(886건·18지역·60개월). `05`로 조회하면 0건이다.

**어긋날 때는 응답을 믿는다.** 단, 응답이 일관될 때만이다. 보충하기 전에 확인했다.

```
조합 57개가 각각 등급명 하나씩만 가짐      이름 충돌 없음
김은 2021~2026 내내 등급 30               연도에 따라 바뀌지 않음
조합마다 단위도 하나씩                     '장' 10장 고정
```

보충은 `004_supplement_codes.sql`에 모은다. 등급명이 `"-"`인 것은 aT가 그렇게
보내기 때문이며, 지어내지 않는다. 원본 CSV는 건드리지 않는다.

이것이 `price_daily`·`price_monthly`에 외래키를 걸지 않은 이유를 사후에 정당화한다.
걸었다면 수산물 백필이 37개 조합에서 멈췄을 것이다. `tracked_targets`만 외래키를
가지므로 보충이 필요하다.

### 3.3 코드 체계

```
부류(6) → 품목(136) → 품종(332) → 등급(693)
```

참조 정합성을 전수 검사했고 고아 행이 없다. 외래키를 그대로 걸 수 있다.

코드표는 `collector/seed/codes/*.csv`에 영문명으로 두고, 포털에서 받은 원본
xlsx는 `collector/seed/reference/`에 원래 이름으로 보존한다.

## 4. 데이터 모델

### 4.1 설계 원칙

1. **응답 필드는 전부 저장한다.** 필드가 20개 미만이고 저장 비용이 사실상 없다.
   일부만 골라 저장하는 것이 오히려 추가 작업이고, 나중에 한 필드가 필요해지면
   스키마 변경·재수집·검증을 다시 해야 한다. 명칭(`item_nm` 등)도 그 시점의 기록으로
   남긴다.
2. **원본을 가공하지 않고 적재하고, 집계·판정은 별도 레이어에서 한다.** 평균만
   남기고 버리면 지역별·등급별 분석이 필요해질 때 5년치를 다시 받아야 한다.
3. **모든 코드는 문자열로 저장한다.** 선행 0이 의미를 가진다.
4. **가격은 integer(원)로 저장한다.** 소수점이 없다.
5. **수집 범위는 좁게 시작한다.** 품목은 나중에 백필이 가능하다.

위 원칙의 근거는 "복원 불가"가 아니라 **재수집 비용**이다. 사용하는 두 API는 모두
기간 조회를 지원하고 2020년 데이터가 있으므로 가격 자체는 다시 받을 수 있다. 과거를
정말 복원할 수 없는 것은 4주치만 제공하는 출하량 API뿐이며 9장에 적었다.

### 4.2 스키마

**구현된 스키마의 정본은 `collector/sql/001_schema.sql`이다.** 이 문서에 DDL을
중복해 적지 않는다 — 두 곳에 두면 반드시 어긋난다. 각 컬럼을 그렇게 정한 이유는
그 파일의 주석에 있다.

```
001_schema.sql            테이블 정의
002_seed_codes.sql        코드표 CSV 적재
003_seed_targets.sql      수집 대상 최초 지정
004_supplement_codes.sql  aT가 코드표에 싣지 않은 코드 보충 (3.2-파)
005_update_targets.sql    데이터가 없던 대상 정리 (3.2-타)
```

번호 파일은 오름차순으로 적용하고, 한 번 적용한 파일은 고치지 않는다. 전부
재실행해도 결과가 같다.

| 테이블 | 담는 것 |
| --- | --- |
| `trade_types` `categories` `items` `varieties` `grades` `regions` | aT 코드 체계. `collector/seed/codes/*.csv`에서 적재 |
| `tracked_targets` | 수집·표시 대상. 품목 추가가 코드 수정이 아니라 행 추가가 된다 |
| `price_daily` | 일별 지역 가격 (지역별 품목별 API) |
| `price_monthly` | 월·연 집계와 산포. 판정의 근거 (연월별 API) |
| `collection_log` | 수집 결과와 호출 수. "데이터 없음"의 세 가지를 구분 |

SQL 파일에 주석으로 담기 어려운 판단 둘을 여기 남긴다.

**가격 테이블에는 마스터로 가는 외래키를 걸지 않는다.** aT가 코드표보다 먼저 새
품종이나 등급을 내보낼 수 있고, 외래키가 있으면 그 행이 거부되어 관측값을 잃는다.
설계 원칙 1번과 직접 충돌한다. 대신 "가격에는 있는데 마스터에 없는 코드"를 찾는
검증 쿼리로 잡는다. `tracked_targets`는 우리가 직접 고른 목록이라 외래키를 건다.

**코드값 열거에는 `enum` 타입 대신 `text` + `CHECK`를 쓴다.** PostgreSQL에서
enum은 값을 더하거나 빼는 작업이 번거롭다. 외부 코드 체계는 변할 수 있다.

### 4.3 아직 만들지 않은 테이블

제철·보관·조리 콘텐츠는 6단계에서 다룬다. 지금 테이블만 만들어두면 몇 주간 비어
있고, 그때 실제 데이터 형태를 보고 정하는 쪽이 낫다. 설계는 아래로 열어둔다.

```sql
-- Peak-taste season. Independent of price; always carries a source,
-- including "generated by AI" when that is where it came from.
CREATE TABLE item_seasons (
    ctgry_cd        text NOT NULL,
    item_cd         text NOT NULL,
    vrty_cd         text NOT NULL,
    peak_from_month smallint,       -- 1-12, NULL when year-round
    peak_to_month   smallint,       -- may wrap: 11 -> 4
    is_year_round   boolean NOT NULL DEFAULT false,
    source          text NOT NULL,
    note            text,
    PRIMARY KEY (ctgry_cd, item_cd, vrty_cd),
    FOREIGN KEY (ctgry_cd, item_cd, vrty_cd)
        REFERENCES varieties (ctgry_cd, item_cd, vrty_cd)
);

CREATE TABLE item_contents (        -- storage, recipes, tips
    id           serial PRIMARY KEY,
    ctgry_cd     text NOT NULL,
    item_cd      text NOT NULL,
    vrty_cd      text NOT NULL,
    content_type text NOT NULL,     -- storage | recipe | tip
    body         text NOT NULL,
    source       text NOT NULL,
    FOREIGN KEY (ctgry_cd, item_cd, vrty_cd)
        REFERENCES varieties (ctgry_cd, item_cd, vrty_cd)
);
```

`is_year_round`가 필요한 이유는 **제철 개념이 약하거나 없는 품목이 섞이기**
때문이다. 축산물이 빠지면서 가장 분명한 예(닭고기)는 사라졌지만, 남은 대상
중에도 시설재배·가공품이 있어 플래그 자체는 그대로 필요하다. 어느 품목을
연중으로 볼지는 제철 정보를 사람이 입력하는 6단계에서 정한다. 제철은 가격과
무관한 편집 데이터이므로(1절) 여기서 추측해 적지 않는다.

## 5. 수집기

### 5.1 동작

```
연월별  (월 1회)
  활성 tracked_targets × 60개월 → UPSERT price_monthly
  지역은 돌지 않는다. sgg_cd를 생략하면 전 지역이 한 번에 온다 (3.2-차)

지역별 품목별  (매일 밤)
  활성 tracked_targets × 지역 → 두 가지를 한다
  sgg_cd가 사실상 필수라 지역마다 호출해야 한다 (3.2-차)
  ① 재동기화: 최근 3주를 기간 조건으로 다시 받아 UPSERT
  ② 백필    : collection_log에 ok/no_survey/out_of_season이 없는 과거 날짜를 채움
```

**두 API의 호출 모양이 다르다는 것이 이 절의 핵심이다.** 같은 줄 수로 적혀 있지만
연월별은 대상 수만큼, 지역별은 대상 × 지역만큼 돈다.

**멱등성이 핵심이다.** `PRIMARY KEY` + `ON CONFLICT DO UPDATE`로 같은 기간을 몇 번
받아도 중복이 생기지 않는다. 이 성질 덕분에 PC가 며칠 꺼져 있어도 켜질 때
따라잡을 수 있고, 클라우드 없이 로컬에서 운영할 수 있다.

### 5.2 "데이터 없음"의 세 가지

구분하지 않으면 수집기가 같은 날짜를 영원히 재시도한다.

| status          | 뜻                          | 재시도             |
| --------------- | --------------------------- | ------------------ |
| `no_survey`     | 주말·공휴일                 | 안 함              |
| `out_of_season` | 그 품종이 시장에 없는 기간  | 안 함 (다음 해 재개) |
| `failed`        | 호출 실패·한도 초과         | 함                 |

공휴일 달력은 두지 않는다. **응답이 비면 `no_survey`로 기록하고 넘어가는 정책**으로
충분하다. 단, (나)에 따라 재동기화 구간 안에서는 다시 확인한다.

### 5.3 호출 관리

일일 한도는 10,000건이고 **잔여량을 조회할 수단이 없다.** `collection_log.api_calls`에
호출 수를 기록해 자체 카운터로 관리한다. 기록하지 않으면 한도 초과로 수집이
실패한 사실조차 모르게 된다.

연월별 백필 규모는 대상별로 실측했다(202111~202610, `totalCount`).

```
쌀 1,286   배추 봄 344 · 여름 530 · 가을 265 · 월동 559
새송이 1,259   복숭아 331   김 886          합계 5,460행
```

페이지로는 10개이므로 **호출 10여 회**다. 일일 한도의 0.1%이고, 백필을 여러 번
다시 돌려도 부담이 없다. **지역을 반복하지 않는 것이 이 수치의 전제다.**

**일별은 다르다.** 지역코드가 사실상 필수라 `대상 8 × 지역 24 = 192회`가 하루
기본이다. 한도 안이지만 연월별의 10배이므로, 재동기화 구간을 늘릴 때 호출 수가
어떻게 늘어나는지 보고 정해야 한다.

### 5.4 설정

`IConfiguration`으로 읽고, 공급자를 겹쳐 쌓는다. 뒤가 앞을 덮는다.

```
appsettings.json   공개 설정. 커밋한다 (At:BaseUrl 등)
User Secrets       aT 서비스 키. ~/.microsoft/usersecrets/<id>/ 에 있어 리포지토리 밖이다
환경변수           나중에 배포 환경에서 덮어쓸 자리 (별도 패키지 필요)
```

**키를 소스나 appsettings.json에 두지 않는다.** 등록은 프로젝트 폴더에서
`dotnet user-secrets set "At:ServiceKey" "<키>"`로 한다. 3단계의 `api/`도 같은
방식을 쓰므로 두 프로젝트의 설정 읽는 법이 같아진다.

## 6. 판정 로직

### 6.1 기준: 과거 같은 시기 대비

```
baseline = 과거 N년(기본 5년) 같은 월의 m_avg_prc 평균
sigma    = 그 m_avg_prc 들의 표준편차          ← 우리가 계산한다
current  = 선택 지역의 최근 조사일 avg_prc

z = (current - baseline) / sigma
```

**연평균 대비가 아니라 같은 월 대비여야 한다.** 딸기는 겨울에 싸고 여름에 비싼 게
정상인데, 연평균과 비교하면 여름 내내 "비싸다"고 표시된다. 그건 정보가 아니다.

**`m_stddev`를 sigma로 쓰면 안 된다.** aT의 `m_stddev`는 *그 달 안에서* 조사일마다
얼마나 흔들렸는지이고, 우리에게 필요한 것은 *해마다 같은 달이* 얼마나 달랐는지다.
서울 쌀 1월로 재면 8배 차이가 난다.

```
해마다의 1월 평균가   50,426 · 52,726 · 53,476 · 56,585 · 59,715
연도간 표준편차       3,616      ← sigma
m_stddev 평균           458

평년값 54,586원에 현재 57,000원이라면
   연도간 사용   z = +0.67   "조금 비싸다"
   m_stddev 사용 z = +5.3    "뚜렷하게 비싸다"   ← 57,000원은 5년 범위 한가운데다
```

aT는 연도간 산포를 제공하지 않으므로 우리가 계산한다. 일별 가격으로 계산할 수도
있지만(일별 API도 5년을 닿는다) 호출이 20회에서 432회로, 저장이 1만 행에서 27만
행으로 늘고, 무엇보다 **월평균을 우리 방식으로 만들게 된다.** 9절의 "통계를 직접
설계하지 않는다"에 어긋나므로 aT의 월평균가를 쓴다.

`m_stddev`는 계속 저장한다. "이번 달 안에서도 들쭉날쭉했다"는 별개의 정보다.

### 6.2 표준편차를 쓰는 이유

`-18%`라는 숫자만으로는 그게 많이 싼 건지 알 수 없다. 배추는 20% 변동이 평범하고
쌀은 5%만 움직여도 큰 사건이다. **품목마다 "정상 범위"가 다르고, 연도간 표준편차가
그 차이를 흡수한다.**

| z            | 표시                     |
| ------------ | ------------------------ |
| ≤ -1.0       | 평년보다 뚜렷하게 싸다   |
| -1.0 ~ -0.3  | 평년보다 조금 싸다       |
| -0.3 ~ 0.3   | 평년 수준                |
| 0.3 ~ 1.0    | 평년보다 조금 비싸다     |
| ≥ 1.0        | 평년보다 뚜렷하게 비싸다 |

경계값은 실제 데이터를 보고 조정한다. `sigma`가 0이거나 NULL이면 z를 쓸 수 없으니
퍼센트 비교로 대체한다 (7-① 참고).

### 6.3 전국 평균은 만들지 않는다

지역별 단순평균은 전국 평균이 아니다. 서울과 안동이 같은 비중을 받고, 어떤 달에
한 지역이 조사에서 빠지면 가격이 안 변했는데도 "전국 평균"이 움직인다.
**사용자가 지역을 직접 고르므로 합칠 일이 없다.** 기본 지역은 서울(`1101`).

## 7. 미결 사항

확인하지 않은 것은 추측하지 않고 여기 모아둔다.

| #  | 확인할 것                                             | 영향                                    | 시점   |
| -- | ----------------------------------------------------- | --------------------------------------- | ------ |
| ③  | 광역도 코드(`3100` 경기 등)에 데이터가 있는 부류가 있는가 | 지역 목록 구성                       | 1단계  |
| ⑥  | 품목별 조사 주기 (쌀만 평일 조사로 확인됨)             | 백필 구멍 판정                          | 1단계  |
| ⑦  | 배추 품종 릴레이를 화면에서 어떻게 이을 것인가         | 아래 참고                               | 4단계  |
| ⑧  | 축산물 등급코드가 응답에서 `"1"`인가 `"01"`인가        | 축산물이 되살아나면                     | 나중   |
| ⑨  | `perRegion`에서 등록 지연을 어떻게 관측할 것인가       | 재동기화 구간 길이 (3.2-나)             | 2단계  |
| ⑩  | 코드표에 없는 조합이 다른 부류·기간에도 더 있는가      | 004 보충 추가                           | 수집 중 |
| ⑪  | 대상마다 조사 지역이 다른 것을 화면에서 어떻게 다룰 것인가 | 지역 선택 UI                        | 4단계  |

**⑪ 대상별 지역 불일치** — 쌀은 24개 지역, 김은 18개 지역에 데이터가 있다. 지역을
먼저 고르는 UI는 "안동을 골랐는데 김이 사라지는" 상황을 만든다. 대상별로 가능한
지역이 다르다는 사실이 스키마에는 이미 들어 있지만(지역이 `price_monthly`의 키),
화면 설계에는 아직 반영돼 있지 않다.

**해결된 것** — ① 소매에서도 `min`/`avg`/`max`가 매일 다르다(3.2-카).
② 새송이버섯은 소매에 5년치가 있다(최근 1년 270건). ④ `515 닭고기`와
`9901 닭` 둘 다 2023년 이후 0건이며 축산물 부류 전체가 그렇다(3.2-타). ⑤ 쌀 품종
`01`은 서울 기준 60개월이 모두 있다. ③은 쌀 소매에서 광역도 코드가 하나도 나오지
않는 것까지 확인했고, 다른 부류는 백필 결과로 판명된다.

**⑦ 배추 품종 릴레이** — 봄·여름(고랭지)·가을·월동이 시간순으로 이어진다.
사용자는 "가을배추값"이 아니라 "배추값"을 보고 싶을 수 있지만, 품종을 이어붙이면
교체 시점에 가격이 점프한다(서로 다른 작물이므로). 품종별 선을 따로 그리고
화면에서 "지금 시장에 있는 품종"을 자동 선택하는 쪽이 정직하다. 스키마는 품종별
저장이라 어느 방식이든 수용한다.

**1단계를 C#으로, 화면 없이 시작한다.** 가장 익숙한 언어로 가장 중요한 자산인

둘로 나뉜다.

`web/`에는 초기 프로토타입을 옮겨둔 `temp/`가 있다. 참고용이며, 4단계에서 새로
작성한다.

## 9. 검토했으나 쓰지 않는 것

나중에 같은 고민을 반복하지 않기 위해 이유를 남긴다.

| 대상                        | 이유                                                                       |
| --------------------------- | -------------------------------------------------------------------------- |
| **기간별 소매가격 조회**    | 시장별 원천. 조사 시장 구성이 시간에 따라 변해 **단순 평균이 가짜 추세를 만든다** (아래). 시장별 세부가 필요해지면 7단계에서 추가 |
| **일별 도·소매 가격정보**   | 같은 이유(`mrkt_cd` 포함). 지역별 품목별이 같은 역할을 집계된 형태로 제공  |
| **최근일자 도·소매가격정보** | 지역 구분이 없어 지역 선택과 축이 맞지 않는다. 1일/1주/1개월/1년 전 비교는 우리가 쌓은 데이터로 계산 가능 |
| **가격 등락 정보**          | 등락률은 파생값. 원값을 저장하면 언제든 계산되지만 역은 불가              |
| **가격 추이 정보**          | 조회일 기준 1~4주 전만 제공. 장기 비교 불가                                |
| **출하량 추이 정보**        | 분류 체계가 가격 API와 다르고(상품대/중/소분류) 매핑 비용이 크다. 4주치만 주므로 **과거 백필이 불가능**하다는 점은 기록해 둔다 |
| **도매시장 계열 전부**      | 경매·정산·경매원천·중도매인·산지공판장. 소매가와 유통 단계가 다름           |
| **전국 평균 직접 계산**     | 6-③ 참고                                                                   |

**시장 구성 변동이 만드는 가짜 추세** — 2026년 10월 서울 쌀(햅쌀) 소매 원천을
보면, 조사 시장이 1곳에서 5곳으로 늘어난다.

```
10/01  B`-유통만 (69,000원)                  평균 3,450원/kg
10/08  + B-유통 (61,900원)                   평균 3,272원/kg   ▼5%
10/22  + I-유통 · 경동 · 복조리              평균 3,285원/kg
```

평균선이 5% 떨어지지만 **B`-유통은 전 기간 69,000원에서 1원도 움직이지 않았고
B-유통도 61,900원 고정이다.** 가격 변동이 아니라 모집단 변동이다. "평소보다 싸다"를
말하는 서비스가 이것을 가격 변화로 오인해 보여주면 서비스 자체가 거짓이 된다.

같은 날 서울 배추 가을 상품이 A-유통 1,930원 / B-유통 3,600원 / 양동(광주)
5,000원으로 **2.6배 차이**가 난다. 섞어서 평균내면 의미가 없다.

**그래서 시군구 단위로 집계된 API를 쓴다.** aT가 자기 방법론으로 처리한 결과를
받고, 우리는 통계를 직접 설계하지 않는다.

`perRegion`의 실제 응답에 **`mrkt_cd`/`mrkt_nm`이 없음을 확인했다.** 시장 컬럼이
존재하지 않으므로 모집단 변동이 우리 쪽 평균에 섞여 들어올 경로가 없다. 가격
필드는 `exmn_dd_{min,avg,max}_prc`와 각각의 `cnvs_` 환산값 6개가 모두 온다.
