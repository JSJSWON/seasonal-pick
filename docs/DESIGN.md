# seasonal-pick 설계 문서

최초 작성 2026-10-25 · 개발 진행에 따라 계속 갱신

---

## 1. 서비스

### 1.1 해결하려는 문제

장을 볼 때 재료의 **절대 가격만** 보고 판단하게 된다. 과거에 얼마였는지 모르니
"오이 5개 1000원"이 싼 건지 알 수 없고, 할인율 20%가 실제로 싼 건지도 모른다.
제철 여부도 찾아보지 않으면 모른다.

이 서비스는 두 가지에 답한다.

1. **이 가격이 평소보다 싼가, 비싼가** — 계산해서 제공
2. **지금이 맛있는 시기인가** — 별도 정보로 제공

### 1.2 두 축은 독립이다

**제철(맛)과 가격(돈)은 서로 다른 축이며, 가격에서 제철을 유도할 수 없다.**
저장 물량이 풀려 싼 시기가 맛있는 시기는 아니고, 제철 초입에는 맛이 절정인데
물량이 적어 비쌀 수 있다.

|            | 싸다 ○            | 싸다 ✕                  |
| ---------- | ----------------- | ----------------------- |
| **제철 ○** | 지금 사라 (목표)  | 맛은 좋을 때, 값은 비쌈 |
| **제철 ✕** | 저장품·수입. 주의 | 살 이유 없음            |

가격만 보여주는 서비스는 사용자를 왼쪽 아래 칸으로 밀어넣는다. 두 축을 함께
보여주는 것이 이 서비스의 존재 이유다.

### 1.3 MVP 범위

**가격 추세 하나**를 제대로 만든다. 제철·보관법·조리법은 그 다음이다.

- 코드표의 6부류를 하나씩
- 월별 추세선 + 현재 가격 위치 + 평년 대비 판정

**화면은 품목을 먼저 고르고 그다음 지역을 고른다.** 지역을 먼저 고르면 "안동을
골랐는데 김이 없다"가 생긴다 — 조사 지역이 품목마다 다르고(3.2-하) 해마다 변하기
때문이다. 품목이 먼저면 그 품목의 지역만 보여주므로 빈 화면이 구조적으로 생기지
않고, 축산물처럼 지역 체계가 다른 부류가 들어와도 그대로 수용된다. 사용자의 실제
질문도 "이 재료가 싼가"이므로 품목이 먼저다(1.1). 기본 지역은 서울.

### 1.4 MVP 대상 품목

부류를 고루 건드려 스키마의 일반성을 검증하는 것이 선정 기준이다. 응답에만 있는
`800 식품`은 성격이 달라(브랜드·용량 지정 제품) MVP에 넣지 않았다 — 확장 후보다
(3.2-파, 8절).

| 부류          | 품목       | 코드      | 품종                                  | 등급        |
| ------------- | ---------- | --------- | ------------------------------------- | ----------- |
| 100 식량작물  | 쌀         | `111`     | `01` 20kg                             | `04` 상품   |
| 200 채소류    | 배추       | `211`     | `01` 봄 `02` 여름 `03` 가을 `06` 월동 | `04` 상품   |
| 300 특용작물  | 새송이버섯 | `317`     | `00` 새송이버섯                       | `04` 상품   |
| 400 과일류    | 복숭아     | `413`     | `01` 백도                             | `04` 상품   |
| 500 축산물    | 닭         | `9901`    | `99` 육계(kg)                         | `1` 육계(kg) |
| 600 수산물    | 김         | `641`     | `00` 마른김                           | `30` (이름 없음) |

**축산물은 품목코드를 갈아서 들어왔다.** 003이 고른 `515 닭고기`가 2023년부터
끊겨서 한동안 5부류였다. 같은 부류에서 살아 있는 `9901 닭 / 99 육계(kg)`로 바꿨다
(006). 지역 체계가 농산물과 다른 것은 품목을 먼저 고르는 구조가 흡수한다(1.3).

**등급이 품목마다 다르다.** `04 상품`이 김에는 없다. 전역 상수로 등급을 고정하면
그 품목들의 수집 결과가 0건이 된다. 김은 한 걸음 더 나가서, 코드표에 없는 등급
`30`으로 제공된다(3.2-파).

쌀 품종 `01`(20kg)과 `05`(20kg 햅쌀)는 별개이며 햅쌀은 가을 한정이다. 연중
추세를 보려면 `01`을 쓴다.

## 2. 시스템 구성

```
[Next.js]  화면 · 그래프                      web/
    │ HTTP (JSON)
    ▼
[ASP.NET Core Web API]  조회 + 판정 로직       api/
    │
    ▼
[PostgreSQL]  가격 이력 · 마스터
    ▲
    │
[수집 워커]  공공데이터 API → DB               collector/
```

**원칙: 수집과 조회를 분리한다.** 사용자 요청이 외부 API를 직접 호출하지 않는다.
외부 API는 일일 호출 한도가 있고 잔여량을 조회할 수단이 없다.

DB의 역할은 "없는 데이터를 만드는 것"이 아니라 **다시 받는 비용을 없애는 것**이다.
API가 기간 조회를 지원하므로 과거를 되받을 수는 있지만(9절), 화면을 그릴 때마다
수천 건을 다시 받을 수는 없다.

수집기는 **콘솔 앱**이다(`collector/SeasonalPick.Collector`). 백필은 한 번 돌고
끝나는 작업이라 호스팅 수명주기가 필요 없고, 매일 돌 재동기화에 스케줄이
필요해지면 지금 만든 클래스들을 호출하는 워커를 덧붙인다. `api/`와는 솔루션을 나눈다 — 함께 빌드할
일이 없고, 수집기는 화면 없이 단독으로 돈다.

## 3. 데이터 소스

### 3.1 사용 API — 1개

```
GET https://apis.data.go.kr/B552845/perRegion/price
    한국농수산식품유통공사_지역별 품목별 도·소매 가격정보
```

**원천은 이것 하나다.** 일별 조사가격을 시군구 단위로 집계한 값이며, 우리가 쓰는
모든 숫자가 여기서 나온다. 월평균·평년값·산포는 **우리가 이 데이터로 계산한다.**

aT는 월 집계를 따로 제공하는 API(연월별)도 갖고 있지만 쓰지 않는다. 파생값이고,
결손이 더 많고, 일별에서 전부 재현되기 때문이다(9절).

```
필수      serviceKey · returnType · pageNo · numOfRows
          cond[exmn_ymd::GTE] · cond[sgg_cd::EQ]
선택      cond[exmn_ymd::LTE] · se_cd · ctgry_cd · item_cd · vrty_cd · grd_cd
          selectable
```

`numOfRows`는 기본 10, 최대 1000. `pageNo` 기본 1. `returnType` 기본 JSON이며
XML을 받으려면 대문자 `XML`로 준다. `selectable`에 컬럼명을 쉼표로 나열하면 응답
컬럼을 골라 받을 수 있다.

**명세 엑셀에 `cond[sgg_cd::EQ]`가 선택으로 적혀 있지만 사실상 필수다** — 빼면
0건이 오고 오류도 아니다(3.2-차). 포털 화면에는 필수 표시가 있다.

기간 조회를 지원하고 **2020년 데이터가 있으며** 응답에 `totalCount`를 제공한다.
백필과 페이징 루프가 성립한다.

수집 범위는 **활성 대상 × 전 지역 × 2020년부터**다.

### 3.2 확인된 API 특성

실제 응답을 보고 확인한 것만 적고, **무엇으로 확인했는지 범위를 함께 적는다.**
설계가 이 사실들에 의존하므로, 범위를 넘겨 일반화하면 설계가 조용히 틀린다.

**(가) 환산가격은 무게 단위일 때만 환산된다**

처음에는 `cnvs_*_prc = *_prc / unit_sz`로 봤다. 표본 4건이 맞았기 때문이다.
**서울 2026년 10월 소매 전체(26개 단위 체계)로 다시 보니 반례가 나왔다.**

```
단위      품목         avg      cnvs    해석
kg 20    쌀        64,138     3,207    /20 → 1kg당          식대로 맞음
kg 5     천일염     12,402     2,480    /5  → 1kg당          맞음
g 100    감자          311     3,113    ×10 → 1kg당          unit_sz로 나누지 않는다
g 50     깻잎        1,443    28,867    ×20 → 1kg당          같음
장 10    김          1,342     1,342    환산하지 않음         식이 깨진다
개 10    오이        8,965     8,965    환산하지 않음
포기 1   배추        6,338     6,338    환산할 것이 없음
```

**규칙은 "unit_sz로 나눈다"가 아니라 "무게 단위면 1kg당으로 환산한다"다.**
`kg`·`g`는 1kg당 가격이 되고, `개`·`장`·`마리`·`구`·`포기`·`봉`·`손`·`묶음`은
환산 없이 원값이 그대로 들어온다.

그래서 **품목 간 비교는 무게 단위 품목끼리만 가능하다.** MVP 대상 중 쌀만
해당하고 배추(포기)·김(장)은 해당하지 않는다. 화면에서 "100g당 얼마" 식으로
품목을 나란히 세우려면 무게를 우리가 알아야 하는데, 모른다.

**축산물에서는 환산값이 아예 깨져 있다.** 서울 2026년 10월을 날짜별로 보면
`cnvs`가 `avg`와 무관하게 **날짜마다 두 값으로 뭉친다.**

```
10/01   cnvs 종류 2가지: 2,930 · 29,300
10/02   cnvs 종류 2가지: 3,032 · 30,320   ← 24행이 30,320, 9행이 3,032
        같은 날 소 안심 20,154원/100g과 수입 삼겹살 1,513원/100g이
        cnvs를 똑같이 30,320으로 받는다
```

날짜별 상수이고 품목·가격과 관계가 없으므로 **환산값이 아니다.** 무엇인지는
확정하지 못했고, 추측하지 않는다.

**결론: `cnvs_*`는 저장만 하고 쓰지 않는다.** 수집기는 계산하지 않고 응답 그대로
넣는다. 판정은 같은 품목·같은 단위끼리의 비교이므로 원값으로 충분하다. 품목 간
비교를 화면에 넣고 싶어지면 그때 무게 단위 품목에 한해 다시 검토한다.

**(나) 과거 날짜 데이터가 나중에 등록된다**

| 조사일 | 등록 시점   | 지연  |
| ------ | ----------- | ----- |
| 10/01  | 10/01 15:16 | 당일  |
| 10/06  | 10/13 16:11 | 7일   |
| 10/08  | 10/13 16:31 | 5일   |
| 10/22  | 10/22 15:06 | 당일  |

**"빈 날짜만 채우기"로는 부족하다.** 10/7에 수집했다면 10/6을 "조사 없음"으로
잘못 확정했을 것이다. 최근 구간을 매번 다시 받아 덮어써야 한다.

당일 데이터는 15시 전후에 등록되므로 수집은 밤에 돌린다.

**단, 이 표의 근거는 9절에서 쓰지 않기로 한 시장 단위 API(`periodRetail`)의
응답이다.** 우리가 쓰는 `perRegion`의 응답에는 `orgnl_reg_dt`가 없어 같은 방식으로
재확인할 수 없다(명세와 실제 응답 모두 확인). **`perRegion`에 등록 지연이 있는지는
모른다.** aT 내부 파이프라인을 추측하지 않는다. 확인 수단은 "어제 비었던 날짜가
오늘 채워졌는가"를 직접 관찰하는 것뿐이고, 수집기가 돌기 전에는 불가능하다(7-⑨).

재동기화는 지연이 있든 없든 손해가 없으므로 그대로 둔다. **단, 구간 길이 "3주"는
근거가 없는 숫자다.** `periodRetail`에서 본 최대 7일 지연에 여유를 더한 값이고,
`perRegion`에서는 측정된 바 없다.

**(다) 조사 주기가 품목마다 다르다**

농수산물은 평일만 조사되고 축산물은 주말에도 조사된다(확인: 서울 2026년).

**그래서 수집기는 요일을 가정하지 않는다.** 공휴일 달력도 두지 않고, 어느 날짜가
비는지 미리 알려 하지도 않는다. 기간을 주고 오는 대로 받는다(5.3).

**(라) 품종이 계절에만 존재한다**

봄배추·가을배추처럼 품종이 아예 없는 기간이 몇 달씩 이어진다(확인: 5년 월별 건수).

**그래서 빈 응답을 오류로 보지 않는다.** 오류로 취급하면 수집기가 그 기간을 영원히
재시도한다(5.3).

**(마) 등급코드는 전역에서 유효하지 않다**

```
등급코드 "1"  →  22개 조합에서 쓰이고 이름이 15가지다
                1++등급 · 삼겹살 · 갈비 · 미국산 · 일반란 · 육계(kg) · …
"M과"         →  14, 15, 25 세 코드
"01" = 1등급  ≠  "1" = 1++등급
```

`grd_cd` 단독으로는 의미가 없고 **(품목, 품종, 등급) 복합으로만** 해석된다.
그리고 `"01"`과 `"1"`이 다른 등급이므로 **정수로 변환하면 데이터가 섞인다.**

**(바) 품목코드 길이가 고정이 아니다** — 3자리 133개, 4자리 7개(`4301 소`, `9901 닭`
등). 004 보충 후 숫자이며, 4자리는 모두 축산물이다.

**(사) 시군구코드에 두 계층이 섞여 있다**

광역도(`3100` 경기), 시(`3111` 수원), 특수(`1000` 전국, `9998` 온라인)가 한 코드
목록에 들어 있다. **합산하면 이중 계산이 된다.**

**그래서 지역을 합치지 않는다.** 사용자가 지역 하나를 고르고 그 지역의 값만 본다
(1.3, 6.5). 합치지 않으므로 계층을 코드로 판별할 필요도 없다.

**(아) 친환경은 구분코드로도 분리된다**

`se_cd`는 `01 소매 / 02 중도매 / 03 친환경농산물 / 07 친환경농산물(신규)`이다.
표고버섯은 등급이 유기농·무농약뿐이고 **소매(`01`)에 데이터가 없다.** 그래서
MVP 품목에서 새송이버섯으로 교체했다. `se_cd`도 품목별로 지정 가능해야 한다.

**(자) 응답 형태 — 값이 전부 문자열이고 필드명이 우리 컬럼명과 다르다**

```
response.body.items.item[]        ← 껍데기가 세 겹이다
response.header.resultCode/resultMsg
response.body.totalCount/numOfRows/pageNo
```

`"pmm_avgprc":"59715"` 처럼 **숫자도 문자열로 온다.** 행이 1건일 때도 `item`은
배열로 왔다(호출 3건에서 확인).

| 응답 필드              | 우리 컬럼      |
| ---------------------- | -------------- |
| `exmn_ymd`             | `exmn_ymd`     |
| `exmn_dd_min_prc`      | `min_prc`      |
| `exmn_dd_avg_prc`      | `avg_prc`      |
| `exmn_dd_max_prc`      | `max_prc`      |
| `exmn_dd_cnvs_min_prc` | `cnvs_min_prc` |
| `exmn_dd_cnvs_avg_prc` | `cnvs_avg_prc` |
| `exmn_dd_cnvs_max_prc` | `cnvs_max_prc` |

코드·이름·단위 필드는 이름을 그대로 쓴다.

변환은 수집기의 `At/` 계층이 담당한다. **API 필드명이 바뀌어도 DB 컬럼명은
그대로 둘 수 있도록** 두 이름을 분리해 둔다.

**(차) 지역 조건이 사실상 필수다 — 빼면 조용히 0건이 온다**

```
2026-10, 쌀 20kg
  날짜 + 지역 1101      6,741건
  날짜 + 부류만             0건     ← resultCode "0" · resultMsg "정상"
```

**오류가 아니라 정상 응답으로 0건이 온다.** 조건을 빼먹은 채 수집기를 돌리면 매일
밤 0건을 받아 전부 `no_survey`로 확정하게 된다. 그래서 호출 전에 필수 조건이
들어갔는지 검사한다(5.3).

따라서 **지역마다 호출해야 하고 `대상 × 지역`이 호출 수가 된다**(5.4).

페이징은 정확하다. `totalCount`와 실제 수신 행 수가 일치하고 중복이 없었다. 루프
종료를 `totalCount`에 걸어도 된다.

**(카) aT의 월 집계는 일별에서 그대로 재현된다**

**이 절이 연월별 API를 쓰지 않는 근거다.** aT가 계산해주는 월 집계가 일별 값의
단순 집계와 같다면, 원천만 받아 우리가 계산하는 쪽이 낫다 — 테이블도 수집기도
하나로 줄어든다.

활성 대상 8개를 서울에서 각 대상의 가장 최근 달로 대조했다.

```
대상           달        일수   일별평균     m_avg      차이    min/max
쌀 20kg       202610    18   63,717.1   63,717    0.00%   둘 다 일치
배추 봄         202607    15    3,491.3    3,491    0.01%   둘 다 일치
배추 여름        202610    18    5,307.0    5,307    0.00%   둘 다 일치
배추 가을        202610     1    4,255.0    4,255    0.00%   둘 다 일치
배추 월동        202605    10    4,513.6    4,514   -0.01%   둘 다 일치
새송이버섯        202610    18      581.6      582   -0.07%   둘 다 일치
복숭아 백도       202609    17   17,653.3   17,653    0.00%   둘 다 일치
김 마른김        202610    18    1,342.0    1,342    0.00%   둘 다 일치
```

**8개 전부 일치한다.** 차이는 최대 0.07%이고 반올림 때문이다. `m_lwprc`·`m_hgprc`도
모두 그 달 일별 평균가의 최소·최대와 정확히 같다.

산포도 재현된다. 월 표준편차를 일별 평균가의 **모표준편차**와 비교했다.

```
쌀 서울 202608       aT 38    계산 37.5   → 반올림 38
새송이 제주 202603    aT 40    계산 39.6   → 반올림 40
```

`m_cv`와 `m_amplitude`는 공식이 정확히 맞지 않았다(0.160 vs 0.141). **설계에서
쓰지 않는 값이므로 더 파지 않는다.** 연 집계(`y_*`)도 쓰지 않는다.

확인 범위는 평균·최소·최대가 8대상 1지역, 표준편차가 2대상 2지역이다.

같은 표본에서 `min`/`avg`/`max`가 모든 일자에 서로 달랐다(20일 중 0일만 동일).
지역 집계인데도 범위가 남아 있으므로 "최저~최고" 표시가 가능하다(7-① 해결).

**단 축산물은 하루에 한 값이다.** `9901 닭` 서울 2026-10은 28일 전부
`min = avg = max`였다. 날마다는 움직이므로(2026년 301일, 3,436~6,682원, 36가지 값)
추세와 판정은 되지만 **그 품목에는 범위 표시가 없다.** 화면이 범위를 전제하면 안
된다.

**(타) 축산물은 품목코드와 지역 체계가 다르다**

003이 고른 `515 닭고기 / 02 도계`는 2023년부터 0건이다. 축산물이 사라진 것이 아니라
**품목코드가 바뀌었다** — 지금은 `4301 소` · `4304 돼지` · `9901 닭` · `9903 계란`
등으로 제공된다. 006이 `9901 닭 / 99 육계(kg)`으로 교체한 이유다.

지역 체계도 다르다. 농산물은 광역시와 시 단위, 축산물은 광역시와 광역도이며 겹치는
곳이 적다. **화면이 품목을 먼저 고르므로**(1.3) 품목마다 자기 지역 목록을 쓰면 되고,
이 차이를 코드가 알 필요가 없다.

**어느 품목에 언제·어디 데이터가 있는지는 적지 않는다.** 그건 aT가 정하는 것이고
우리가 통제할 수 없다. 기간을 넉넉히 주고 오는 대로 받으며, 표본이 모자란 칸은
판정하지 않는다(6.2).

**(파) 코드표가 응답보다 불완전하다**

aT가 응답으로 내보내는 코드 중 일부가 aT 자신의 코드표 엑셀에 없다. 6부류 최근
1년 35,664행을 훑은 결과다.

```
응답에서 본 (부류,품목,품종,등급) 조합   209개
그중 코드표에 없는 조합                  37개
    등급만 없음 27 · 품종까지 없음 8 · 품목까지 없음 4
```

김 마른김이 대표적이다. 코드표는 등급 `05 중품`만 싣고 있지만 **실제 데이터는 등급
`30`으로 6년 내내 제공된다**(886건·18지역·60개월). `05`로 조회하면 0건이다.

**어긋날 때는 응답을 믿는다.** 단, 응답이 일관될 때만이다. 보충하기 전에 확인했다.

```
조합 57개가 각각 등급명 하나씩만 가짐      이름 충돌 없음
김은 2021~2026 내내 등급 30               연도에 따라 바뀌지 않음
조합마다 단위도 하나씩                     '장' 10장 고정
```

**범위를 넓혀 더 있는지 확인했다.** 2022년 소매에는 추가 누락이 없고, 중도매
(`se_cd=02`)에만 4개 더 있다(녹두 중국·페루, 단감 서촌 상품·중품). 친환경
(`03`·`07`)에는 없다.

**그런데 이 검사에 결함이 있었다.** 부류를 `100`~`600`으로 **열거해서** 조회했는데,
그 목록은 우리 코드표에서 가져온 것이다. **코드표가 빠뜨린 부류는 그 방식으로
찾을 수 없다.** 열거하지 않고 한 지역의 한 달을 통째로 받아 세니 부류가 7개였다.

```
서울 2026-10 소매 3,637행
  100 식량작물 270 · 200 채소류 872 · 300 특용작물 198 · 400 과일류 454
  500 축산물 902 · 600 수산물 797
  800 식품 144      ← 코드표에 없다
```

`800 식품`은 **브랜드와 용량이 지정된 가공식품** 8종이다 — 즉석밥·두부·김치·
고추장·된장·간장·맛김·콩나물. 서울 2022-01에 160행, 2020-01에는 0행이므로 2022년에
생긴 것으로 보인다. 연월별에도 1,712행 있었으니 **API가 바뀐 것이 아니라 우리 검사가
놓친 것이다.** `007`에서 부류·품목·품종·등급을 보충했다.

**총 45개 조합이 코드표에 없었다**(소매 기준). 004의 37개와 007의 8개다. 004의
37개 중 36개는 일별 응답에서도 다시 확인했다(나머지 `663 전어`는 5년에 65건인
희소 품목이라 표본 달에 들지 않았다).

보충은 `004_supplement_codes.sql`에 모은다. 등급명이 `"-"`인 것은 aT가 그렇게
보내기 때문이며, 지어내지 않는다. 원본 CSV는 건드리지 않는다.

이것이 `price_daily`에 외래키를 걸지 않은 이유를 사후에 정당화한다. 걸었다면
수산물 백필이 37개 조합에서 멈췄을 것이다. `tracked_targets`만 외래키를
가지므로 보충이 필요하다.

**(하) 어느 지역에 데이터가 있는지는 물어봐야 안다**

코드표의 시군구 38개 중 데이터가 오는 곳은 일부다. 비는 곳이 있고, 품목에 따라
다르고(농산물 24 · 김 18 · 닭 18), 해마다 늘어왔다(쌀 2022년 19개 → 최근 23개).
광역도 코드는 축산물만 담는다.

**그래서 목록을 만들어 두지 않는다.** 백필이 38개를 전부 물어보고, 그 결과가
"어디에 데이터가 있는가"의 유일한 근거가 된다(5.1). 화면도 품목을 먼저 고른 뒤
그 품목에 데이터가 있는 지역만 보여준다(1.3).

`regions.level`(광역시/시/도)은 **내가 코드 번호를 보고 분류한 것**이다. 목록을
묶어 보여줄 때만 쓰고, 어떤 지역을 보여줄지 결정하는 데는 쓰지 않는다.

### 3.3 코드 체계

```
코드표 원본        부류 6 → 품목 136 → 품종 332 → 등급 693
004 보충 후        부류 6 → 품목 140 → 품종 340 → 등급 730
007 보충 후        부류 7 → 품목 148 → 품종 348 → 등급 738
```

**부류는 6개가 아니라 7개다.** 코드표에 없는 `800 식품`이 응답에 있다(3.2-파).

원본은 참조 정합성을 전수 검사했고 고아 행이 없다. 보충분도 부모를 먼저 넣어
외래키가 유지된다.

코드표는 `collector/seed/codes/*.csv`에 영문명으로 두고, 포털에서 받은 원본
xlsx는 `collector/seed/reference/`에 원래 이름으로 보존한다.

## 4. 데이터 모델

### 4.1 설계 원칙

1. **값 필드는 전부 저장한다.** 응답이 21개 필드이고 저장 비용이 사실상 없다.
   일부만 골라 저장하는 것이 오히려 추가 작업이고, 나중에 한 필드가 필요해지면
   스키마 변경·재수집·검증을 다시 해야 한다.

   **명칭(`item_nm` 등)은 예외다.** `price_daily`에는 코드만 넣고 이름은 코드표에
   한 번만 둔다. 이름은 관측값이 아니라 코드의 속성이고, 15만 행마다 7개 컬럼을
   반복하는 값이 아니다. 코드표에 없는 코드가 응답에 나오면(3.2-파) 그때 이름까지
   함께 코드표로 보충하므로, 그 시점의 이름은 보존된다.
2. **원본을 가공하지 않고 적재하고, 집계·판정은 별도 레이어에서 한다.** 평균만
   남기고 버리면 지역별·등급별 분석이 필요해질 때 5년치를 다시 받아야 한다.
3. **모든 코드는 문자열로 저장한다.** 선행 0이 의미를 가진다.
4. **가격은 integer(원)로 저장한다.** 확인한 응답에서 가격 6개 필드가 모두
   정수였다. 우리가 계산하는 평균·표준편차는 소수이므로 집계 쿼리에서 다룬다.
5. **수집 범위는 좁게 시작한다.** 품목은 나중에 백필이 가능하다.

위 원칙의 근거는 "복원 불가"가 아니라 **재수집 비용**이다. 사용하는 API는 기간
조회를 지원하고 2020년 데이터가 있으므로 가격 자체는 다시 받을 수 있다. 과거를
정말 복원할 수 없는 것은 4주치만 제공하는 출하량 API뿐이며 9장에 적었다.

### 4.2 스키마

**구현된 스키마의 정본은 `collector/sql/001_schema.sql`이다.** 이 문서에 DDL을
중복해 적지 않는다 — 두 곳에 두면 반드시 어긋난다. 각 컬럼을 그렇게 정한 이유는
그 파일의 주석에 있다.

```
001_schema.sql            테이블 정의
002_seed_codes.sql        코드표 CSV 적재
003_seed_targets.sql      수집 대상 최초 지정
004_supplement_codes.sql  aT가 코드표에 싣지 않은 코드 보충 (3.2-파)
005_update_targets.sql    데이터가 없던 대상 정리 (3.2-타)
006_add_chicken_target.sql  축산물을 9901 닭으로 교체해 6부류 복구
007_supplement_food_category.sql  코드표에 없는 800 식품 부류 보충 (3.2-파)
```

`001`을 고치면 빈 DB에 다시 적용해 현재 DB와 컬럼·제약을 대조한다. 손으로 고친
스키마와 파일이 어긋나는 것을 그때 잡는다.

번호 파일은 오름차순으로 적용한다. **틀린 것은 그 파일을 고친다.** 번호 파일을
건드리지 않는 관례는 여러 환경이 이미 그 파일을 적용해버린 경우를 위한 것인데,
지금은 DB가 하나뿐이라 고치고 전부 재실행하는 쪽이 정확하다.

**대신 고친 뒤에는 재실행해 결과를 확인한다.** 이미 적용된 파일을 고치면 그 수정은
자동으로 반영되지 않으므로, 재실행이 유일한 검증 수단이다.

단 **`001`은 멱등이 아니다.** `CREATE TABLE`에 `IF NOT EXISTS`가 없어 두 번째
실행은 실패한다. 일부러 그렇게 둔다 — `IF NOT EXISTS`를 붙이면 테이블이 이미
있을 때 컬럼 변경이 조용히 무시되어, 스키마가 파일과 다른데도 성공한 것처럼
보인다. `001`은 빈 DB에 한 번 적용하고, `002`~`005`는 몇 번이든 재실행한다.

환경이 둘 이상 생기면(배포 서버 등) 그때부터는 새 번호 파일로 가야 한다. 그 시점에
이 규칙을 다시 적는다.

| 테이블 | 담는 것 |
| --- | --- |
| `trade_types` `categories` `items` `varieties` `grades` `regions` | aT 코드 체계. `collector/seed/codes/*.csv`에서 적재 |
| `tracked_targets` | 수집·표시 대상. 품목 추가가 코드 수정이 아니라 행 추가가 된다 |
| `price_daily` | **유일한 원천.** 일별 지역 가격 |
| `collection_log` | 수집 결과와 호출 수. "데이터 없음"의 세 가지를 구분 |

**월 집계 테이블은 없다.** 월평균·평년값·산포는 `price_daily`에서 집계해 쓴다.
같은 사실을 두 곳에 두면 어긋나고(4.2 머리말), 15만 행 집계는 PostgreSQL에서
즉시 끝난다. 느려지면 그때 materialized view로 올린다.

SQL 파일에 주석으로 담기 어려운 판단 둘을 여기 남긴다.

**가격 테이블에는 마스터로 가는 외래키를 걸지 않는다.** aT는 코드표에 없는 품종·
등급을 실제로 내보낸다(3.2-파, 37개 조합). 외래키가 있으면 그 행이 거부되어
관측값을 잃는다.
설계 원칙 1번과 직접 충돌한다. 대신 "가격에는 있는데 마스터에 없는 코드"를 찾는
검증 쿼리로 잡는다. `tracked_targets`는 우리가 직접 고른 목록이라 외래키를 건다.

**코드값 열거에는 `enum` 타입 대신 `text` + `CHECK`를 쓴다.** PostgreSQL에서
enum은 값을 더하거나 빼는 작업이 번거롭다. 외부 코드 체계는 변할 수 있다.

### 4.3 아직 만들지 않은 테이블

제철·보관·조리 콘텐츠는 5단계에서 다룬다. 지금 테이블만 만들어두면 몇 주간 비어
있고, 그때 실제 데이터 형태를 보고 정하는 쪽이 낫다. 설계는 아래로 열어둔다.

```sql
-- Peak-taste season. Independent of price; always carries a source,
-- including "generated by AI" when that is where it came from.
CREATE TABLE item_seasons (
    ctgry_cd        text NOT NULL,
    item_cd         text NOT NULL,
    vrty_cd         text NOT NULL,
    peak_from_month smallint,       -- 1-12, NULL when year-round
    peak_to_month   smallint,       -- may wrap: 11 -> 4
    is_year_round   boolean NOT NULL DEFAULT false,
    source          text NOT NULL,
    note            text,
    PRIMARY KEY (ctgry_cd, item_cd, vrty_cd),
    FOREIGN KEY (ctgry_cd, item_cd, vrty_cd)
        REFERENCES varieties (ctgry_cd, item_cd, vrty_cd)
);

CREATE TABLE item_contents (        -- storage, recipes, tips
    id           serial PRIMARY KEY,
    ctgry_cd     text NOT NULL,
    item_cd      text NOT NULL,
    vrty_cd      text NOT NULL,
    content_type text NOT NULL,     -- storage | recipe | tip
    body         text NOT NULL,
    source       text NOT NULL,
    FOREIGN KEY (ctgry_cd, item_cd, vrty_cd)
        REFERENCES varieties (ctgry_cd, item_cd, vrty_cd)
);
```

`is_year_round`가 필요한 이유는 **제철 개념이 약하거나 없는 품목이 섞이기**
때문이다. 축산물이 빠지면서 가장 분명한 예(닭고기)는 사라졌지만, 남은 대상
중에도 시설재배·가공품이 있어 플래그 자체는 그대로 필요하다. 어느 품목을
연중으로 볼지는 제철 정보를 사람이 입력하는 5단계에서 정한다. 제철은 가격과
무관한 편집 데이터이므로(1절) 여기서 추측해 적지 않는다.

## 5. 수집기

### 5.1 동작

```
재동기화  (매일 밤)
  활성 tracked_targets × 데이터가 있는 지역 × 최근 3주 → UPSERT price_daily

전체 백필  (처음 한 번, 그 뒤 월 1회)
  활성 tracked_targets × 전 지역 38 × 2020년부터 → UPSERT price_daily
```

**빈 날짜를 추적하지 않는다.** 어느 날짜가 비었는지 기록해 두고 다시 채우러 가는
구조를 쓰지 않는다 — 대신 전체 백필을 주기적으로 다시 돌린다. 멱등이라 몇 번
돌려도 같고, 호출 400회는 한도의 4%다. **aT가 언제 등록할지 예측하지 않고,
주기적으로 다시 물어볼 뿐이다.**

그래서 두 가지가 저절로 해결된다.

```
재동기화 창(3주)보다 늦게 등록된 데이터   → 다음 전체 백필이 가져온다
aT가 새로 추가한 조사 지역              → 다음 전체 백필이 발견한다
```

**두 번째가 특히 중요하다.** 재동기화는 지역 목록을 `price_daily`에서 가져오므로
(아래) 한 번도 데이터가 없던 지역은 영원히 묻지 않는다. 조사 지역은 실제로
늘어왔다(쌀 2022년 19개 → 최근 23개). 전체 백필만이 그것을 알아낼 수 있다.

**둘은 같은 코드에 기간과 지역 목록만 다르게 준다.** `sgg_cd`가 사실상 필수라
지역마다 호출하고(3.2-차), `collection_log.job`이 둘을 구분한다.

**지역 목록은 수집기가 스스로 알아낸다.**

```
백필     regions 38개를 전부 돈다
재동기화  price_daily에 그 대상의 행이 있는 지역만 돈다
```

어느 지역이 어느 대상을 조사하는지는 **물어보기 전에 알 수 없다** — API가 지역 없이
는 답하지 않는다(3.2-차). 그리고 조사 지역은 해마다 늘어왔다(3.2-하). 그래서 측정해
둔 숫자를 코드에 박지 않고, 백필이 전수로 확인한 결과를 재동기화가 이어받는다.
**수집한 데이터만이 "어디에 데이터가 있는가"의 근거다.**

실측: 김을 38개 지역으로 돌려 16개에서 행이 나왔고, 이어서 돌린 재동기화는 16개만
돌았다.

### 5.2 구현

```
Program.cs                   backfill | resync 분기, 인자 해석
At/AtApiClient.cs            호출 + 페이징 + 재시도. DB를 모른다
At/PriceRow.cs               응답 1행. 전부 string (aT가 그렇게 보낸다)
At/TargetCodes.cs            코드 5개 묶음
Db/PriceDailyRepository.cs   500행씩 UPSERT
Db/RegionRepository.cs       전체 지역 / 데이터가 있는 지역
Db/CollectionLogRepository.cs 실행 기록, 당일 호출 수 집계
Jobs/CollectJob.cs           대상 × 지역 루프
```

`--target`과 `--region`으로 한 조합만 돌릴 수 있다. 전체를 돌리기 전에 작은 범위로
확인하는 용도다.

**멱등성이 핵심이다.** `PRIMARY KEY` + `ON CONFLICT DO UPDATE`로 같은 기간을 몇 번
받아도 중복이 생기지 않는다. 이 성질 덕분에 PC가 며칠 꺼져 있어도 켜질 때
따라잡을 수 있고, 클라우드 없이 로컬에서 운영할 수 있다.

### 5.3 비어 있는 날짜는 진단하지 않는다

응답이 비는 이유는 네 가지다 — 주말, 공휴일, 그 품종이 시장에 없는 기간(3.2-라),
그리고 **아직 등록되지 않음**. 호출 시점에는 이 넷을 구분할 방법이 없다.

**그래서 구분하지 않는다.** `collection_log.status`는 `ok`와 `failed`뿐이고, 성공한
호출이 0행을 돌려주면 `ok` + `row_count 0`이다. 그건 사실이고, 이유는 추측이다.

나중에 이유가 필요해지면 `price_daily`에서 나온다.

```
어떤 날짜에 다른 대상·지역의 행이 있다   → 그날은 조사가 있었다
그런데 이 대상에는 그 날짜가 없다        → 이 품종이 그때 시장에 없었다
```

**공휴일 달력도 두지 않는다.** 둘 필요가 없다 — 비면 비는 대로 두고, 주기적 전체
백필이 나중에 채워지는 것을 가져온다(5.1).

**단, 빈 응답을 받기 전에 조건을 검사한다.** `perRegion`은 `sgg_cd`가 빠져도 정상
응답으로 0건을 주므로(3.2-차), 필수 조건이 들어갔는지 확인하지 않으면 **우리 버그가
"데이터 없음"처럼 보인다.** 수집기는 지역 코드가 비면 호출하지 않고 예외를 던진다.

**등록 지연을 `orgnl_reg_dt` 없이 관측했다.** 2026-10-30 00:06에 서울을 조회했을
때 쌀·김·새송이 모두 최근 조사일이 10/28(수)이고 **10/29(목)이 비어 있었다.**
공휴일이 아니므로 "아직 등록 안 됨"과 "그날 조사 없음" 둘 중 하나였다.

같은 날 늦게 수집기로 같은 범위를 받으니 **10/29가 들어왔다.**

```
10/30 00:06   10/01 ~ 10/28  (19일 중 18일)
10/30 이후    10/01 ~ 10/29  (19일)       ← 10/29가 나타남
```

**조사가 없던 날이 아니라 아직 등록되지 않았던 날이었다.** 지연이 존재한다는 것은
이것으로 확정됐다.

**최대 며칠 늦는지는 알 필요가 없다.** 알아야 재동기화 창을 정할 수 있다고 봤는데,
주기적 전체 백필이 있으면 창을 넘긴 것도 다음 백필이 가져온다(5.1). 창은 공짜로
넉넉히 두면 된다 — 기간을 늘려도 호출 수가 변하지 않으므로(5.4) 3주를 쓴다.

**화면도 지연을 설명하지 않는다.** 오늘이 10/30인데 마지막 조사일이 10/23이면
10/23 데이터를 보여주고 그 날짜를 함께 표시한다. aT가 언제 등록하는지는 우리가
통제하지 못하고, "못 채웠다"를 따로 알릴 가치도 없다.

### 5.4 호출 관리

일일 한도는 10,000건이고 **응답으로 잔여량을 알 수 있는 수단이 없다**(포털 화면에
현황이 있는지는 확인하지 않았다). `collection_log.api_calls`에
호출 수를 기록해 자체 카운터로 관리한다. 기록하지 않으면 한도 초과로 수집이
실패한 사실조차 모르게 된다.

**백필(한 번)** — 서울에서 대상별 5년 건수를 실측했다.

```
쌀 1,218   배추 봄 267 · 여름 376 · 가을 187 · 월동 464
새송이 1,222   복숭아 237   김 1,222   닭 1,666     서울 합계 6,859행

농산물 7개 × 24지역 ≈ 9.5만   김 × 18지역 ≈ 2.2만   닭 × 18지역 ≈ 3.0만
                                                     합계 약 15만 행
```

**백필은 5년 누적 지역을, 재동기화는 최근 지역을 쓴다.** 둘이 다르다 — 의정부
(`3113`)처럼 과거에는 조사됐고 최근에는 비는 지역이 있다(3.2-하). 과거를 받을 때
그 지역을 빼면 있는 데이터를 놓친다.

**실제로 돌렸다**(2020-01-01 ~ 2026-10-30).

```
조합 342   행 161,895   호출 410   실패 0   소요 40분 53초   테이블 40 MB
  쌀 34,053 · 새송이 33,729 · 닭 30,077 · 김 24,666 · 배추 4종 33,369 · 복숭아 6,001
  지역 24 (농산물) · 18 (김·닭) · 합집합 33
```

추산은 "약 15만 행 · 호출 300~400회"였고 실측이 161,895행 · 410회다.

**시간은 전부 API 대기다.** 한 조합(쌀 서울 전 기간, 호출 2회 · 1,670행)이 14초
걸리는데 그중 CPU는 1.8초다. 호출당 6초 정도이고 `410 × 6초 ≈ 41분`이 실측과 맞는다.
**UPSERT는 병목이 아니므로** binary COPY로 바꿀 이유가 없다(500행 묶음 유지).

**재동기화(매일)** — `대상 × 지역`만큼 돈다(3.2-하).

```
농산물 7개 대상 × 23지역  +  김 16지역  +  닭 18지역  =  195회
제철이 아닌 대상은 그 기간 0건이므로 실제로는 더 적다
```

**하루 195회가 상한이고 한도의 2.0%다.** 재동기화 구간을 3주에서 늘려도 호출 수는
변하지 않는다 — 한 번의 호출이 기간 조건으로 여러 날을 가져오기 때문이다. 늘어나는
것은 응답 행 수뿐이다. **그래서 창을 좁힐 이유가 없다.**

**합쳐서** — 전체 백필을 월 1회 돌리면 그날은 `195 + 400 = 595회`로 한도의 6%다.
여유가 충분하므로 주 1회로 올려도 된다. 빈 날짜를 추적하는 로직을 만드는 대신 이
여유를 쓴다(5.1).

### 5.5 설정

`IConfiguration`으로 읽고, 공급자를 겹쳐 쌓는다. 뒤가 앞을 덮는다.

```
appsettings.json   공개 설정. 커밋한다 (At:BaseUrl 등)
User Secrets       aT 서비스 키. ~/.microsoft/usersecrets/<id>/ 에 있어 리포지토리 밖이다
환경변수           나중에 배포 환경에서 덮어쓸 자리 (별도 패키지 필요)
```

**키를 소스나 appsettings.json에 두지 않는다.** 등록은 프로젝트 폴더에서
`dotnet user-secrets set "At:ServiceKey" "<키>"`로 한다. 2단계의 `api/`도 같은
방식을 쓰므로 두 프로젝트의 설정 읽는 법이 같아진다.

## 6. 판정 로직

### 6.1 기준: 과거 같은 시기 대비

```
월평균   = 그 달 조사일들의 avg_prc 평균            price_daily에서 집계
baseline = 과거 N년 같은 월의 월평균의 평균
sigma    = 그 월평균들의 표준편차
current  = 선택 지역의 최근 조사일 avg_prc

z = (current - baseline) / sigma
```

**전부 `price_daily` 하나에서 나온다.** 월평균은 aT의 월 집계와 같은 값이고
(3.2-카), 2020년부터 받으므로 같은 월의 표본이 6~7개다.

백필 후 쌀·서울·10월로 실제 계산해봤다.

```
연도별 10월 월평균
  2020 55,761 · 2021 54,010 · 2022 47,224 · 2023 57,767
  2024 50,866 · 2025 66,840 · 2026 63,674

평년값(2020~2025, 표본 6) 55,411   sigma 6,137
2026년 10월 63,674 → z = +1.35     "평년보다 뚜렷하게 비싸다"
```

**집계 테이블 없이 `price_daily` 쿼리 하나로 나온다.**

**연평균 대비가 아니라 같은 월 대비여야 한다.** 품목 가격에는 계절 주기가 있고,
연평균과 비교하면 비싼 계절 내내 "비싸다"로 표시된다. 그건 정보가 아니다.
우리 데이터에서는 품종 자체가 계절에만 존재하기도 한다(3.2-라).

**달 안의 산포를 sigma로 쓰면 안 된다.** 그 달 조사일들의 표준편차는 *그 달
안에서* 얼마나 흔들렸는지이고, 우리에게 필요한 것은 *해마다 같은 달이* 얼마나
달랐는지다. 서울 쌀 1월로 재면 8배 차이가 난다.

```
해마다의 1월 평균가   50,426 · 52,726 · 53,476 · 56,585 · 59,715
연도간 표준편차       3,616      ← sigma
달 안 표준편차 평균      458

평년값 54,586원에 현재 57,000원이라면
   연도간 사용   z = +0.67   "조금 비싸다"
   달 안 사용    z = +5.3    "뚜렷하게 비싸다"   ← 57,000원은 5년 범위 한가운데다
```

**aT는 연도간 산포를 제공하지 않는다.** 어차피 우리가 계산해야 하므로, 월평균까지
직접 집계하는 것이 원천을 하나로 줄이는 쪽이다(9절).

달 안의 산포도 함께 계산해 보여줄 수 있다. "이번 달 안에서도 들쭉날쭉했다"는 별개
정보다.

### 6.2 표준편차를 쓰는 이유

`-18%`라는 숫자만으로는 그게 많이 싼 건지 알 수 없다. 배추는 20% 변동이 평범하고
쌀은 5%만 움직여도 큰 사건이다. **품목마다 "정상 범위"가 다르고, 연도간 표준편차가
그 차이를 흡수한다.**

| \|z\|          | 표시                               | 비중 |
| ------------- | ---------------------------------- | ---- |
| < 0.5         | 평년 수준                          | 27%  |
| 0.5 ~ 1.35    | 평년보다 조금 싸다 / 비싸다        | 53%  |
| ≥ 1.35        | 평년보다 뚜렷하게 싸다 / 비싸다    | 19%  |

**관례가 아니라 우리 데이터에서 자른 값이다.** 표본 5개 이상인 6,795개 칸의 실제
분포에서 "뚜렷하게"가 5분의 1쯤 되도록 잘랐다.

**±1 / ±2 같은 정규분포 경계는 여기 적용되지 않는다.** 표준편차를 같은 n개 점에서
내므로 `|z|`가 `√(n-1)`에 묶인다. 측정값이 이론값과 거의 같았다.

```
표본  건수   |z| 최대   √(n-1)
  2    108     1.00      1.00     ← 두 점은 평균에서 같은 거리. 항상 1.00
  3    543     1.41      1.41
  5    975     1.99      2.00
  7   4788     2.30      2.45
```

**그래서 최소 표본은 5개다.** 2개면 `|z|`가 언제나 정확히 1.00이고(108건 전부),
3·4개는 상한이 1.41·1.73이라 "뚜렷하게" 경계가 의미를 갖지 못한다. 5개부터 상한이
2.00이 된다. 표본 5개 이상이 전체 칸의 83%이고, 나머지는 **가격과 추세만 보여주고
판정하지 않는다.**

**표본 수는 쿼리할 때 그 칸에서 센다.** "닭은 4.8년"처럼 품목별 사정을 코드에 넣지
않는다 — aT가 언제부터 무엇을 제공하는지는 우리가 통제하지 못하고 계속 변한다.

**세 숫자는 `appsettings.json`에 있다**(`MinimumSampleSize` · `SlightThreshold` ·
`StrongThreshold`). 품목 6개로 자른 잠정값이라 품목이 늘면 다시 봐야 하고, 코드를
고치지 않고 조정할 수 있어야 한다.

### 6.3 품종을 이어붙이지 않는다

배추는 봄·여름(고랭지)·가을·월동이 시간순으로 이어진다. 한 줄로 합치면 "배추값"이
되어 읽기 쉽지만, **교체 지점마다 가격이 뛴다.** 서울 5년을 측정한 결과다.

```
202206 봄    4,114  →  202207 여름  6,652   +61.7%
202211 여름  4,339  →  202212 가을  2,723   -37.2%
202404 월동  4,666  →  202405 봄    3,817   -18.2%
교체 16회, 변화율 중위값 18.4%
```

서로 다른 작물이므로 당연한 차이인데, 한 선으로 그리면 **가격이 안 변했는데 선이
뛴다.** 9절의 "가짜 추세"와 같은 구조다.

게다가 60개월 중 **22개월은 두 품종이 동시에 조사된다**(202207: 봄 4,590 · 여름
6,652). "지금 시장에 있는 품종"이 하나로 정해지지 않는다.

**그래서 품종별로 선을 따로 그리고 판정도 품종별로 한다.** 평년값과 sigma는 같은
품종의 같은 월에서만 나와야 의미가 있다. 화면 기본값은 최근 조사일이 가장 최신인
품종이고, 두 품종이 함께 있는 달에는 둘 다 보여준다.

### 6.4 조회 API와 화면

```
GET /api/targets                            품목 목록
GET /api/targets/{id}/regions               그 품목의 지역 + 최근 조사일
GET /api/targets/{id}/prices?region=1101    추세 · 현재가 · 판정
```

**품목을 먼저 고르는 순서가 그대로 엔드포인트가 된다**(1.3). 지역 목록은
`price_daily`에서 나오므로 "지금 우리가 가진 것"만 제시한다.

지역마다 **최근 조사일을 함께 내려준다.** 과거에만 조사된 지역이 섞이는데(김은 18개
중 강릉 2023-06 · 춘천 2024-03이 끊겼다) "며칠까지가 최신인가"를 API가 정하면 그게
임의 기준이 된다. 날짜를 주고 화면이 판단한다.

`prices` 응답은 `latest`(조사일·최저·평균·최고·단위), `monthly`(추세선), `verdict`로
나뉜다. `verdict.available`이 `false`면 **가격과 추세선만 보여주고 판정 문구를 내지
않는다.** `latest.date`를 그대로 내려 화면이 "10/29 기준"을 표시한다(5.3).

**집계는 SQL, 판정은 C#이다.** 월평균은 `GROUP BY`가 할 일이고, baseline·sigma·z와
문구 매핑은 산수다. 경계값이 앞으로 바뀔 값이라 단위 시험을 붙일 수 있는 쪽에 둔다.

`Db/Database.cs`는 수집기의 같은 파일을 복제했다. 겹치는 것이 연결 생성 20줄뿐이라
세 번째 프로젝트를 만드는 것보다 싸다. 겹치는 양이 늘면 그때 라이브러리로 뺀다.

**화면의 선택은 전부 URL에 있다.**

```
/?target=2&region=1101
```

품목·지역을 쿼리 파라미터로 두고 서버 컴포넌트에서 API를 부른다. 클라이언트 상태가
없어 어긋날 것이 없고, 새로고침과 링크 공유가 되며, **서버끼리 부르므로 API에 CORS가
필요 없다.** 선택지는 버튼이 아니라 링크다.

**추세선은 SVG로 직접 그린다.** 선 하나와 점 하나라 차트 라이브러리를 넣지 않았다.
축·툴팁·확대가 필요해지면 그때 고른다. 추가한 npm 패키지는 없다.

**조사가 없던 기간은 선을 끊는다.** 가을배추는 10~1월에만 있는데 한 줄로 이으면
1월과 다음 10월 사이 여덟 달을 가로지르는 선이 생긴다 — 9절이 거부한 가짜 추세와 같은
모양이다. 연속된 달끼리만 선으로 잇고, 한 달짜리 구간은 점으로 둔다. x축을 순번이
아니라 시간으로 잡아야 이것이 가능하다.

**다크 모드는 지원하지 않는다.** `create-next-app`이 넣어준 `prefers-color-scheme`
블록이 본문 배경만 검게 만들어 흰 카드가 검은 바탕에 떠 있었다. 스타일 가이드를
정한 뒤에 제대로 하는 편이 낫다(프로젝트 태스크 1).

### 6.5 전국 평균은 만들지 않는다

지역별 단순평균은 전국 평균이 아니다. 서울과 안동이 같은 비중을 받고, 어떤 달에
한 지역이 조사에서 빠지면 가격이 안 변했는데도 "전국 평균"이 움직인다.
**사용자가 지역을 직접 고르므로 합칠 일이 없다.** 기본 지역은 서울(`1101`).

## 7. 미결 사항

확인하지 않은 것은 추측하지 않고 여기 모아둔다. **지금 열려 있는 항목은 없다.**
새로 생기면 여기 적고, 해결되면 아래로 옮긴다.

⑰(판정 경계값)은 **잠정 해결**이다. 품목 6개 데이터로 자른 값이라 품목이 늘면 다시
봐야 하고, 그래서 설정 파일에 있다.

## 9. 검토했으나 쓰지 않는 것

나중에 같은 고민을 반복하지 않기 위해 이유를 남긴다.

| 대상                        | 이유                                                                       |
| --------------------------- | -------------------------------------------------------------------------- |
| **연월별 도·소매가격정보**  | 파생값. 월평균·최소·최대·표준편차가 일별에서 그대로 재현되고(3.2-카), 결손은 더 많다(지역당 평균 54/60개월). 원천 하나만 받고 가공은 우리가 한다 |
| **기간별 소매가격 조회**    | 시장별 원천. 조사 시장 구성이 시간에 따라 변해 **단순 평균이 가짜 추세를 만든다** (아래). 시장별 세부가 필요해지면 6단계에서 추가 |
| **일별 도·소매 가격정보**   | 같은 이유(`mrkt_cd` 포함). 지역별 품목별이 같은 역할을 집계된 형태로 제공  |
| **최근일자 도·소매가격정보** | 지역 구분이 없어 지역 선택과 축이 맞지 않는다. 1일/1주/1개월/1년 전 비교는 우리가 쌓은 데이터로 계산 가능 |
| **가격 등락 정보**          | 등락률은 파생값. 원값을 저장하면 언제든 계산되지만 역은 불가              |
| **가격 추이 정보**          | 조회일 기준 1~4주 전만 제공. 장기 비교 불가                                |
| **출하량 추이 정보**        | 분류 체계가 가격 API와 다르고(상품대/중/소분류) 매핑 비용이 크다. 4주치만 주므로 **과거 백필이 불가능**하다는 점은 기록해 둔다 |
| **도매시장 계열 전부**      | 경매·정산·경매원천·중도매인·산지공판장. 소매가와 유통 단계가 다름           |
| **전국 평균 직접 계산**     | 6.5 참고                                                                   |

**시장 구성 변동이 만드는 가짜 추세** — 2026년 10월 서울 쌀(햅쌀) 소매 원천을
보면, 조사 시장이 1곳에서 5곳으로 늘어난다.

```
10/01  B`-유통만 (69,000원)                  평균 3,450원/kg
10/08  + B-유통 (61,900원)                   평균 3,272원/kg   ▼5%
10/22  + I-유통 · 경동 · 복조리              평균 3,285원/kg
```

평균선이 5% 떨어지지만 **B`-유통은 전 기간 69,000원에서 1원도 움직이지 않았고
B-유통도 61,900원 고정이다.** 가격 변동이 아니라 모집단 변동이다. "평소보다 싸다"를
말하는 서비스가 이것을 가격 변화로 오인해 보여주면 서비스 자체가 거짓이 된다.

같은 날 서울 배추 가을 상품이 A-유통 1,930원 / B-유통 3,600원 / 양동(광주)
5,000원으로 **2.6배 차이**가 난다. 섞어서 평균내면 의미가 없다.

**그래서 시군구 단위로 집계된 API를 쓴다.** aT가 자기 방법론으로 처리한 결과를
받고, 우리는 통계를 직접 설계하지 않는다.

`perRegion`의 실제 응답에 **`mrkt_cd`/`mrkt_nm`이 없음을 확인했다.** 시장 컬럼이
존재하지 않으므로 모집단 변동이 우리 쪽 평균에 섞여 들어올 경로가 없다. 가격
필드는 `exmn_dd_{min,avg,max}_prc`와 각각의 `cnvs_` 환산값 6개가 모두 온다.
